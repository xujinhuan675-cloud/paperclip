# Paperclip 产品生产交接包

> 状态：工作版，可用于需求拆分、设计评审和开发交接。
> 
> 目标：依据当前 Paperclip 的完整源码和源码文档，整理出一条合理的产品复现路线。实现者不需要复制原代码，但应能按照本目录完成功能和交互一致的产品。

## 先看什么

1. [产品定义](01-product-definition.md)：确认产品解决什么问题，以及不解决什么问题。
2. [能力地图](02-capability-map.md)：确认产品由哪些能力组成。
3. [产品架构](04-product-architecture.md)：理解模块之间如何协作。
4. [核心流程](05-core-flows.md)：理解用户从目标到执行结果的完整路径。
5. [版本路线](07-version-roadmap.md)：确认先做什么、后做什么。
6. `requirements/`：按需求进入设计、开发和验收。
7. `acceptance/`：按验收场景判断是否完成。

## 这套资料是什么

这是面向开发交接的产品规格包，包含：

- 产品目标、角色和核心对象；
- 功能结构和模块边界；
- 页面、状态、流程和治理规则；
- 版本拆分、依赖关系和开发顺序；
- 每个需求的交互、规则、异常和验收标准；
- 产品可见的执行状态、成本、预算、失败恢复和审计要求。

## 这套资料不是什么

- 不是 Paperclip 原作者的历史开发记录；
- 不是源码逐文件翻译；
- 不要求使用相同的框架、数据库或代码结构；
- 不包含生产部署和基础设施运维方案；
- 不把实验性页面自动视为必须进入第一版的核心能力。

## 推荐使用方式

### 产品经理

先读产品定义、能力地图和版本路线，再按需求文件检查范围、依赖和验收标准。

### 设计人员

重点阅读核心流程、状态模型和对应需求文件中的交互规则、空状态、异常状态和权限提示。

### 开发人员

从版本路线和开发顺序进入，逐个完成需求文件中的用户结果、业务规则、数据状态、接口边界和验收条件。

### 测试人员

从 `acceptance/` 和需求文件的验收场景开始，优先覆盖主流程、拒绝路径、重复执行、超时、预算暂停和恢复。

## 证据标记

- **事实**：源码、源码文档或可定位的实际行为直接支持。
- **推断**：根据多个事实拼接出的产品规则或推荐路线，不代表原作者历史顺序。
- **决策**：为了复现目标而采用的明确产品选择。
- **待决策**：现有资料冲突或证据不足，需要产品负责人确认。

## 权威来源顺序

1. 当前源码和测试行为；
2. 仓库内当前有效的规范文档；
3. Code Review Graph 的调用关系和执行流；
4. Zread Wiki 或公开 Wiki 的结构化摘要；
5. 产品愿景、路线图和历史计划。

来源之间冲突时，不隐藏冲突，进入 [证据与待决策](evidence/open-questions.md) 记录。

## 交付原则

- 以当前最终能力为目标，只规划一条合理复现路线。
- 采用纵向切片，每个版本都必须形成可操作的产品闭环。
- 先定义对象、状态、权限和结果，再展开页面和任务。
- 保留完整规则和边界；通过摘要、链接、模板和分层阅读降低理解成本。
- 每个需求必须能追溯到流程、模块、证据和验收标准。
