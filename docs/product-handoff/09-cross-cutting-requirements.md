# 09 横切产品要求

## 性能与反馈

这里的性能只记录会影响产品行为和用户决策的内容，不规定具体基础设施方案。

- 创建和分配操作应给出明确的提交中、成功或失败反馈。
- Run 启动后应能看到队列、运行、等待、失败或完成状态。
- 长时间执行必须显示最后更新时间，避免用户误以为系统无响应。
- 状态轮询、事件流和日志展示不能阻塞核心操作。
- 重复点击、重复唤醒和网络重试不能造成重复执行。
- 成本和预算更新应与 Run 关联，允许用户判断是否继续。

## 可观察性

用户至少需要看到：

- 当前 Agent、Issue 和 Run 状态；
- 触发来源，例如手动、分配、评论、定时或审批；
- 最近进度、最后更新时间和错误摘要；
- 运行耗时、成本和预算影响；
- Workspace、工具和连接是否可用；
- 是否等待 Approval；
- 产生了哪些 Artifact 或部分结果；
- 谁执行了暂停、恢复、改派或预算覆盖。

## 失败和恢复

- 错误需要分类为用户输入、权限、预算、连接、执行、环境或系统恢复问题。
- 每类错误都要说明是否可重试、由谁处理和可能的副作用。
- 重试必须有上限、退避和幂等规则。
- 恢复不能悄悄改变 Issue 负责人或重复产生外部副作用。
- 用户取消后，界面要区分“已请求取消”和“已确认停止”。

## 安全与治理

- 所有核心数据和调用都继承 Company 隔离。
- Secret 不应直接出现在普通日志、评论或 Artifact 中。
- Tool 和连接授权必须具备范围、审批、过期和撤销语义。
- 代理执行的外部副作用必须可归因到 Agent、Issue、Run 和人类批准。
- 审批不是装饰性页面，而是能阻止或释放实际副作用的控制点。

## 结果质量

- Issue 完成必须有结果证据或明确的无需产物说明。
- Artifact 要能回到生成它的 Issue、Run 和 Agent。
- 部分失败不能被 UI 显示为完整成功。
- 用户应能区分草稿、待审查、已批准、已发布和已归档结果。

## 文档与验收

- 每个需求至少有一个正向和一个负向验收场景。
- 关键规则必须同时覆盖 UI、API、服务和持久化行为。
- 文档中的事实、推断、决策和待决策必须分开。
- 任何无法从源码或文档确认的行为，不得写成无条件的产品承诺。
